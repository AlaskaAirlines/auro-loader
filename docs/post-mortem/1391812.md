# AB#1391812

## Executive Summary

Today, the `auro-loader` spinner is just an animation — it can't tell a guest what's happening or why a wait is taking a while. This work adds an **optional descriptive message** next to the loading animation, which can also **rotate through several messages** over time (for example, "Hang tight…" → "Thanks for your patience…" → "This may take a moment…" — deliberately interchangeable phrasing, since the rotation loops back to the first message after the last, and any wording that implies a real-world procedural order would read as going backward once it wraps around). Teams can also choose which side of the animation the message appears on (top, right, bottom, or left), and the message/fallback text now automatically scales with the loader's own size (extra small through large) instead of always rendering at one fixed size regardless of how big or small the animation is. Guests who have "Reduce Motion" turned on see the most relevant text available — their custom fallback text if they set one, otherwise the message content rather than a generic "Loading…" — and never see two competing pieces of text at once. Nothing about this changes how any existing loader already in use looks or behaves — the feature is entirely opt-in. Several independent rounds of code review, plus hands-on testing and direct content feedback, caught and closed a long series of real defects along the way, including two separate cases where a claim of "no visual change" turned out to be wrong until it was fixed and re-verified, and a defensive CSS fallback that was extended until it caused the exact kind of problem it was meant to prevent.

Ticket: [AB#1391812](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1391812)

## The Problem

Many of Alaska's loading states are open-ended — the app can't say how long a spinner will keep spinning. With no way to pair the spinner with reassuring text, a 15–25 second wait can feel like the app is stuck, which increases the chance a guest gives up and abandons what they were doing. The native app already solves this by pairing its loader with rotating reassurance text; this work brings the web experience to the same standard.

## Root Cause

Fourteen unrelated defects surfaced across many rounds of review, each worth recording on its own:

1. **Reduced-motion visibility gating was asymmetric.** `event.target.assignedNodes({ flatten: true })` on an *empty* default slot returns the slot's own fallback content (the `Loading...` text node), not nothing — an unguarded flatten call could see "content" a consumer never provided, latching `has-default-content` permanently true. Separately, the CSS gating which text shows under reduced motion was applied to only one side of the pair: `.message-region` was correctly gated, but `.no-animation` (the default-slot fallback) had no matching gate and was `display: block` unconditionally, so a `message`-slot-only consumer could see both texts at once. Both fixed by symmetric, content-aware gating on `has-message`/`has-default-content`.
2. **A mechanical stylelint re-nest silently dropped a property.** The pre-existing `pulse` loader relied on `:host([pulse]) > .loader-shape > span { position: relative; }` to override the base `.loader-shape > span { position: absolute; }`, so its three dots would lay out inline via `margin` instead of stacking at the same coordinates. When `_pulse.scss` was restructured into nested SCSS to fix unrelated stylelint errors, `position: relative` was preserved on `:host([pulse])` and on `.loader-shape`, but never re-added to the innermost `> span` block — a straightforward copy-and-restructure slip, not a logic change, but the resolved CSS was silently different afterward. This is a second, independent instance of the same category of defect as the original `.loader-shape` wrapper regression from the first round of work (see Iterations): touching shared/inherited CSS structure without diffing the *resolved* output before and after.
3. **A geometry-based regression test can be defeated by an unrelated animation.** The first attempt at a regression test for defect #2 asserted that the three pulse spans' `getBoundingClientRect().left` values were distinct. It passed even with the bug reintroduced, because `pulse`'s `@keyframes` animation combined with each span's staggered `animation-delay` puts every span at a slightly different point in its `transform: scale()` cycle at the instant the assertion runs — enough to produce slightly different bounding rects regardless of whether `position` was actually correct. The fix was to assert directly on `getComputedStyle(span).position === "relative"` instead of an indirect geometry side-effect, then prove it by reverting the CSS fix and confirming the test failed before restoring it.
4. **A shared library moved a design token without a compatible fallback.** `@aurodesignsystem/webcorestylesheets`'s `.body-default` class (used by this component's fallback and message text) reads `font-weight: var(--wcss-body-default-weight, )` — note the empty fallback. That token's concrete value (`450`) now lives only in the package's theme stylesheet, which `auro-loader` never imports. Consumers who separately load Auro's global theme never noticed; anyone who doesn't would silently get the browser's default font-weight. Two independent code-review tools each found this independently by diffing the dependency's compiled CSS across versions, not by reading source. Fixed defensively by defining the same custom property, with the same value, directly in this component's own `tokens.scss` — though see defect #13 below, where this same fallback was later found to have overreached.
5. **A property self-correction ran in the wrong Lit lifecycle hook.** The `messageInterval`/`messagePosition` self-correction was originally written inside `updated()`. Mutating a reactive property from `updated()` — after the current render has already completed — is a documented Lit anti-pattern: it schedules a brand-new update cycle rather than folding into the one already in progress, which a review tool confirmed by actually running the test suite and observing Lit's own runtime warning ("scheduled an update ... after an update completed," see `https://lit.dev/msg/change-in-update`). Moved to `willUpdate()`, which runs *before* the render it's guarding.
6. **A new size-scaling feature reintroduced the same cascade-order bug class as the size attributes it built on.** A later addition, `getFontSize()`, maps the loader's `xs`/`sm`/`md`/`lg` size attributes to a `body-*` text class using an if/else chain originally ordered `xs` first. But when more than one size attribute is set on the same loader (e.g. `xs lg` together), the *animation's* actual size is decided by CSS specificity/source order in `_base.scss`, where `lg`'s block is declared last and therefore wins. The two logics disagreed: combining size attributes could render an 8rem animation next to `body-xs` (0.75rem) text. Reordered `getFontSize()` to check `lg`/`md` before `sm`/`xs`, matching the CSS's own source-order priority.
7. **`laser`'s "no text in any motion state" rule was enforced explicitly for one text region but only implicitly for the other.** `_laser.scss` set `display: none` explicitly on `.message-region` under `:host([laser])`, but left `.no-animation` (the default-slot fallback) hidden only as a side effect of `:host([laser])`'s own `height: 0; overflow: hidden`. Both regions are now hidden by the same explicit rule, so a future change to laser's sizing can't silently un-hide the fallback text.
8. **A validity check duplicated across two call sites can drift.** `messageInterval`'s validity predicate was written out separately in `willUpdate()` and `_startMessageCycle()` (the second copy needed because `_startMessageCycle()` can run, via `connectedCallback`, before `willUpdate()` has had a chance to self-correct an invalid initial attribute). Extracted into one shared `isValidMessageInterval()` helper so the two call sites can no longer disagree.
9. **The interval-validity check accepted an unusable value on one end and rejected a valid one on the other.** Two gaps in that same helper, found in the same review round: (a) no upper bound — a `message-interval` above `2^31 - 1` (the largest delay `setInterval` supports) passed validation and then silently overflowed in the browser, firing near-immediately instead of after the requested delay; (b) `Number.isFinite()` doesn't coerce, so a numeric *string* set directly on the `messageInterval` property (as a framework wrapper binding an input's value would do) failed validation and was silently reset to the default, even though the identical string reaches a valid value when set through the HTML attribute (already coerced by Lit's `fromAttribute` converter). Fixed with an explicit `MAX_MESSAGE_INTERVAL_MS` ceiling and a `Number(value)` coercion before validating either way; `willUpdate()` now also stores the coerced numeric value back onto the property so its runtime type matches its documented type.
10. **A microtask queued before disconnect can still run after there's no lifecycle hook left to undo it.** `_startMessageCycle()` had no guard against running after the element had already left the document: a `slotchange` event queued just before a synchronous `disconnectedCallback` could still fire afterward, calling `_startMessageCycle()` on a detached element and arming a `setInterval` that nothing would ever clear again. Fixed with an `isConnected` guard at the top of `_startMessageCycle()`, covering every call site (connect, slot change, interval-property change, reduced-motion change) with one check.
11. **A newly-added browser API call had no feature detection, unlike everything else in this component.** `connectedCallback()` started unconditionally calling `window.matchMedia(...)` to watch the reduced-motion preference — a dependency this component never had before this feature. Consumers testing the component in a bare jsdom environment (a common, well-known gap: jsdom does not implement `matchMedia` without an explicit polyfill) would get an uncaught `TypeError` on every mount. Guarded behind `typeof window.matchMedia === "function"`.
12. **Reflecting a property with `reflect: true` and a concrete default writes that default into every instance's DOM, not just customized ones.** `messageInterval`/`messagePosition` reflected unconditionally, so *every* `<auro-loader>` — including ones that never touch the message feature — gained `message-interval="5000"` and `message-position="bottom"` attributes after first render, contradicting this branch's own repeated claim that non-message loaders are DOM-unchanged. Fixed with a custom Lit `converter` whose `toAttribute` returns `null` (removing the attribute entirely) when the value equals the default.
13. **A defensive CSS fallback, once extended, became worse than the problem it solved.** The `--wcss-body-default-weight: 450` fallback added for defect #4 was extended to `--wcss-body-xs/sm/lg-weight` when the size-scaling feature introduced those additional text classes. Because the fallback is set unconditionally on `:host`, it always wins the cascade over a consumer's own theme value for that same custom property, regardless of the theme's own selector specificity — the opposite of what a fallback should do, which is defer to anything else that provides a value. There is no way to keep a `:host`-scoped declaration deferential to an unknown external theme, so it was removed entirely rather than made conditional.
14. **Example content that implies a real-world sequence breaks once the underlying mechanism loops.** The original example messages ("Checking your bags…" → "Confirming your seat…" → "Almost there…") read as a linear procedural checklist ending in near-completion. Since cycling wraps back to the first message after the last, "Almost there…" followed by "Checking your bags…" again visibly regresses. Replaced with interchangeable reassurance phrasing that carries no inherent order (see Iterations for the intermediate revision that still had this problem).

## The Fix

`src/auro-loader.js` gained a new named slot, `message`, that accepts one or more elements of any type:

```html
<auro-loader orbit message-position="top" message-interval="4000">
  <span slot="message">Hang tight...</span>
  <span slot="message">Thanks for your patience...</span>
  <span slot="message">This may take a moment...</span>
</auro-loader>
```

- **Slot tracking**: a `slotchange` handler reads `assignedElements()` from the `message` slot and toggles the native `hidden` attribute on each element to show exactly one at a time — no re-rendering or re-parenting of consumer-owned nodes. Any element type rotates, not just `<li>`; the internal wrapper is a plain `<div>` rather than a `<ul>` (a `<ul>` requiring `<li>` children was the original design, but restricting to `<li>` was reversed — see Iterations below).
- **Cycling**: a `messageInterval` property (`message-interval` attribute, default `5000`ms) drives a `setInterval` that only starts when more than one message is slotted, the type isn't `laser`, and the element is still connected to the document. The timer is always cleared before a new one is set, cleared again on `disconnectedCallback`, restarted from index 0 whenever the slotted content changes mid-cycle, and restarted in `connectedCallback` too (covering a DOM move/reparent that fires disconnect→connect without a `slotchange`). `_advanceMessage` guards against an empty message list to avoid a `NaN` index.
- **Interval validation**: a shared `isValidMessageInterval()` helper coerces its input and checks it's a finite number strictly between `0` and `2^31 - 1` (the largest delay `setInterval` supports), falling back to the 5000ms default otherwise — whether the invalid or oversized value arrived via the HTML attribute or was set directly on the property. `willUpdate()` self-corrects the *property* (storing the coerced numeric value, not just using it for the timer), so an invalid `message-interval="abc"` doesn't linger in the DOM as the literal, confusing attribute `message-interval="NaN"`.
- **Positioning**: a `messagePosition` property (`message-position` attribute: `top` | `right` | `bottom` | `left`, default `bottom`) controls `:host`'s flex-direction. An invalid value (e.g. a typo like `"buttom"`) self-corrects back to `bottom` the same way.
- **Attribute reflection stays DOM-neutral for unconfigured loaders**: `messageInterval` and `messagePosition` both reflect to their attributes via a custom Lit `converter`, but that converter's `toAttribute` returns `null` — removing the attribute — whenever the value equals the property's own default. A loader that never sets `message-interval`/`message-position` never gains those attributes in its DOM, matching the "existing loaders are unchanged" guarantee at the attribute level, not just visually.
- **Accessibility**: the message region carries `role="status"`, `aria-live="polite"`, `aria-atomic="false"`; `::slotted([hidden])` is hardened with `!important` so a consumer's own `display` rules on the slotted elements can't defeat the rotation. Under reduced motion, rotation stops entirely and **freezes on whichever message was active** when the preference took effect — it does not reset to the first message.
- **Reduced motion, fully content-aware**: two `slotchange`-driven host attributes — `has-message` and `has-default-content` — track which slots actually have real content (as opposed to the default slot's built-in `Loading...` fallback). Both the default slot's fallback text **and** the `message` region are gated on these attributes, so exactly one piece of text is ever shown: the default slot's real content if it has any, otherwise the message, otherwise the generic fallback.
- **`laser` type**: the `message` slot and the default/static-label slot are both hidden by one explicit rule for `laser`, in any motion state, and no rotation timer runs for it — matching `laser`'s pre-existing, intentional lack of room for text.
- **Reduced-motion watcher is feature-detected**: `connectedCallback()` only sets up the `prefers-reduced-motion` media-query watcher when `window.matchMedia` exists, so consumers testing this component in environments without it (e.g. bare jsdom) don't get an uncaught error on mount.
- **Message/fallback text now scales with the loader's own size.** A private `getFontSize()` method maps the loader's size — `xs` → `body-xs`, the unsized default → `body-sm`, `sm` → `body-default`, `md`/`lg` → `body-lg` (the unsized default sits between `xs` and `sm` in actual rendered size, so its text class does too) — and applies it to both the default-slot fallback and the `message` region, instead of always using a fixed `body-default` class regardless of how large or small the animation is. A new `apiExamples/message-size.html` and a "Message Size" section in the prose docs demonstrate all five sizes side by side.
- **Styling**: placeholder CSS custom properties (`--ds-auro-loader-message-color`, `--ds-auro-loader-message-spacing`), marked `TODO(design)`, plus a new `_message.scss` partial.
- **Layout restructuring**: the spinner's spans/svg were wrapped in a new `.loader-shape` container so `:host` could become a flex container laying out the animation and the message region together, while leaving `:host`'s rendered size identical when no message is present. `:host` also kept its `position: relative`, restored after review caught that the restructuring had silently dropped it.
- **Stylelint cleanup**: the touched SCSS files were brought to zero stylelint errors introduced by this feature — flat combinator selectors converted to proper SCSS nesting, property order and duplicate-selector issues fixed, and the handful of violations that are structurally unavoidable or intentional are suppressed with a `stylelint-disable` and one canonical explanatory comment in `_base.scss`.
- **CEM/manifest accuracy**: `onDark`/`onLight` now carry an `@deprecated` JSDoc tag and an explicit `attribute: "ondark"`/`"onlight"` mapping, so the generated manifest's attribute name matches what actually binds in HTML.
- **Documentation trimmed for the consuming engineer**: the `@slot` JSDoc was shortened to one sentence each, with full nuance left to the prose docs (`docs/partials/api.md`). `docs/api.md`'s hand-maintained table was kept in sync, including `onDark`/`onLight`'s alphabetical position.
- **Example content revised twice for a looping rotation.** The rotating example messages went through two revisions before landing on wording with no implied order at all — see Root Cause #14 and Iterations.
- **Removed an overreaching CSS fallback.** The `--wcss-body-*-weight: 450` safety net (Root Cause #4, then extended for the size-scaling feature) was removed from `tokens.scss` entirely — see Root Cause #13.

## Why This Works

The `message` slot is fully independent of the existing default (unnamed) slot — there's no shared markup or selector between the two, so populating one never interferes with the other's own rendering. Toggling `hidden` on the slotted elements (rather than re-rendering them) keeps consumer-attached state/listeners on those nodes intact and gives the accessibility tree a single, predictable mutation per cycle for the live region to announce. Gating the interval behind `_messages.length > 1`, `!this.laser`, and `this.isConnected` means a single message, a `laser`-type loader, or a detached element never spins up (or keeps alive) a needless timer, and clearing the timer unconditionally before setting a new one — on slot change, on interval-property change, on connect, and on disconnect — rules out leaked or duplicate timers regardless of how the element enters or leaves the DOM, including the microtask-ordering edge case in Root Cause #10.

The reduced-motion behavior is symmetric by construction: both text sources are gated by the same pair of attributes, so there is no code path where both are visible at once, and no code path where neither is. `getFontSize()`'s size priority now deliberately mirrors `_base.scss`'s own cascade order rather than an independently-chosen priority, so the two can't disagree about which attribute wins when a loader combines more than one size. The interval validator coerces its input the same way regardless of whether the value arrived through the HTML attribute or was set directly on the property, so the two entry points can't reach different conclusions about the same value. The attribute-reflection fix keeps a plain, unconfigured `<auro-loader>` truly unchanged at the DOM level — not just visually — by only ever writing an attribute when its value differs from the default. Removing the font-weight fallback (rather than trying to scope it more narrowly) accepts a small, known gap (a consumer who loads neither this component's own styles nor Auro's theme gets the browser's default weight) in exchange for never silently overriding a real theme, which is the safer failure mode for a "fallback" to have.

## Outcome

Loaders across the product can now carry a short, optionally rotating message — of any content type, not just plain list items — that tells guests what's happening during a wait, without any visual or behavioral change to loaders that don't use the new capability. Teams also get control over which side of the animation the message appears on, and the message/fallback text now visually matches the loader's own size instead of always rendering at one fixed size. Guests with "Reduce Motion" enabled always see exactly one, correctly-chosen piece of guidance text, frozen on whichever message was showing rather than jumping back to the first one.

Beyond the original two `xhigh`-effort two-model code reviews and two passes of a differently-scoped review skill, this branch went through several further rounds of review — including another full two-model `xhigh` pass — plus direct, non-automated content feedback, which together surfaced and closed a long tail of additional real defects: a text-size/animation-size cascade mismatch, an incompletely-enforced `laser` text-hiding rule, duplicated and gap-ridden interval validation (missing upper bound, missing string coercion), a disconnect-timing timer leak, an unguarded new browser API dependency, attributes being reflected onto every loader instance regardless of configuration, a CSS fallback that had grown to override consumers' own themes, and rotating example text that read as a broken procedural sequence once it looped. A clean `auro build` + `auro cem-check` pass and a dependency-hygiene check (only `devDependencies` version-range bumps, no new runtime dependency) confirmed none of this hardening introduced new manifest or packaging problems. 32 automated tests continue to cover the new slot, cycling, cleanup, accessibility attributes, positioning, the `laser` exclusion, the content-aware reduced-motion behavior, and non-`<li>` content — though the size-scaling logic and the new interval upper bound still have no dedicated test coverage (see Learnings).

## Learnings

- **Mechanical refactors of shared/inherited CSS need the resolved output diffed, not just the source.** Two separate incidents in this branch — the original `.loader-shape` wrapper hiding every animation type, and a later stylelint re-nest dropping `position: relative` from `pulse` — were both "the source looks like a faithful restructuring" mistakes that only a compiled-CSS comparison (or, in the second case, an adversarial test) caught.
- **A geometry assertion (`getBoundingClientRect`) is not a reliable proxy for a static CSS property when an animation is in play.** Assert directly on `getComputedStyle(...).position` for this kind of check instead of an indirect geometry side-effect.
- **"No visual change" and "no DOM change" are claims that need to survive an adversarial check, not just a plausible read of the diff.** Three separate incidents in this branch shipped with one of those exact claims before being disproven by review: the `.loader-shape` wrapper, the `pulse` regression, and the always-reflected `messageInterval`/`messagePosition` attributes.
- **A dependency version bump can change compiled CSS output even when nothing in the repo's own source changed** — and a defensive fallback for that class of problem can itself overreach if it's scoped too broadly. Setting a concrete fallback value unconditionally on `:host` means it always wins the cascade over anything a consumer's own theme provides for that same custom property, which defeats the purpose of a "fallback." When a genuine gap can't be closed without risking that, it can be more correct to accept the narrower, known gap (removal) than to paper over it.
- **A JS priority decision and a CSS cascade decision over the same set of boolean attributes must be checked against each other, not chosen independently.** `getFontSize()`'s size priority and `_base.scss`'s selector source order each made a reasonable-looking, self-consistent choice — but they disagreed, and only combining more than one size attribute at once exposed it. Any future component that maps multiple boolean modifiers to both a CSS outcome and a JS-computed outcome should verify the two use the same priority order.
- **A newly-added browser API dependency needs the same feature-detection discipline as anything else the component didn't previously depend on.** Consumers commonly test web components against a partial DOM implementation (jsdom); an unconditional `window.matchMedia(...)` call broke an assumption those consumers' test suites relied on, for a component that had no prior dependency on it.
- **`reflect: true` with a concrete default writes that default into every instance's DOM, not just configured ones.** A custom Lit `converter.toAttribute` that returns `null` at the default value keeps a component's unconfigured usages DOM-neutral, matching the intuitive meaning of "this attribute wasn't set."
- **Validate the same way regardless of entry point.** `isValidMessageInterval()` originally only checked `Number.isFinite()`, which doesn't coerce strings — the HTML-attribute path already coerced via Lit's `fromAttribute`, but the JS-property path did not, so the identical value could pass through one entry point and fail through the other.
- **Rotating example/documentation text that implies a real-world procedural order breaks down as soon as the underlying mechanism loops.** Both this branch's original example messages and its first revision read as sequential steps toward completion; wrapping back to the first message after the last then reads as regression, not progress. Interchangeable, order-agnostic phrasing is the safer default for any content that will cycle indefinitely.
- **A stale test fixture can be mistaken for an undocumented, load-bearing usage pattern.** The test suite's long-standing use of `<li>` (a leftover from a design already reversed once — see Iterations) led a review pass to conclude consumers likely did the same and to flag a missing CSS reset for it. Checking every real example first showed the pattern had no actual users; the fix was cleaning up the stale tests, not defending runtime behavior nobody exercises.
- **Independent review tools converging on the same non-obvious finding by different methods is a strong signal, not a coincidence to shrug off** — as happened twice in this branch's history (the font-weight regression, found by diffing dependency output, and the Lit lifecycle anti-pattern, found by reading an actual runtime console warning).
- **Several lower-severity findings from later review rounds were surfaced but intentionally left unfixed for this round**, to avoid open-ended scope growth: no dedicated test coverage yet for `getFontSize()`'s size-to-class mapping or for the new interval upper bound; `.hidden` doesn't hide an `<svg slot="message">` (SVGElement doesn't implement that IDL property); the live region re-announces on every rotation tick with no opt-out; `message-position="top"/"left"`'s `column-reverse`/`row-reverse` changes visual order without changing DOM order (a WCAG 1.3.2 consideration, low-impact today since nothing in the region is focusable); and `has-message`/`has-default-content` aren't documented as component-owned, consumer-observable attributes. These are recorded here so a future contributor knows they were seen and consciously deferred, not missed.
- Lit does not auto-hyphenate camelCase property names into kebab-case attributes — needs an explicit `attribute:` mapping or the HTML attribute is silently ignored.
- `assignedNodes().length > 0` is not a valid "has content" check — it counts whitespace-only text nodes between tags, which exist in virtually every real multi-line usage of a slotted component.
- CSS specificity, not source order, decides who wins inside a media query: an attribute selector on `:host` beats a bare `:host` even when the bare rule is the one wrapped in the more specific media query.
- `<auro-loader>` has no default animation — every animation is opt-in via a boolean type attribute (`orbit`, `pulse`, `ringworm`, `laser`). Documentation examples must always pair with one of these.
- Uncommitted work on a long-running branch is fragile, and so is git history touched by autonomous tooling: at multiple points across this feature's history, changes silently disappeared from an uncommitted working tree between turns, and separately, a background review agent with write access amended a commit multiple times without that being a distinctly reported action. Committing incrementally, and re-checking `git log`/`git reflog` rather than trusting a prior turn's summary of what's committed, both reduce this risk.
- This repo's generated `docs/api.md` (via the older `web-component-analyzer` CLI) is broken by an earlier, unrelated housekeeping commit that deleted `scripts/wca/auro-loader.js`; it's hand-maintained now and needs manual updates kept in sync with JSDoc.

## Iterations That Didn't Work

- **A stylelint-driven restructuring of `_pulse.scss` that silently dropped `position: relative`.** Caught by code review, not by the existing test suite (the existing "should have three elements" test only counted `<span>`s, so it passed regardless of layout). Fixed by restoring the property and adding a test that asserts the computed `position` value directly.
- **A `getBoundingClientRect()`-based regression test for the pulse fix.** The `pulse` animation's `transform: scale()` with staggered delays perturbs bounding rects regardless of `position`, so the test passed even with the bug deliberately reintroduced. Replaced with a direct `getComputedStyle` assertion, verified by revert-and-retest.
- **Hiding only the `message` region under reduced motion, leaving the default-slot fallback unconditional** — replaced with symmetric, content-aware gating on both sides.
- **Freezing the message on reduced motion instead of hiding it, then hiding it unconditionally** — both replaced by the current content-aware behavior.
- **`.loader-shape` wrapper shipped without updating dependent selectors or preserving all of `:host`'s prior properties** — broke every loader type's visibility and separately dropped `position: relative` from `:host` itself; both caught by user report and code review respectively.
- **Renaming classes to camelCase to satisfy the shared stylelint config's `selector-class-pattern` rule.** Reverted every rename and used a justified `stylelint-disable` instead, since kebab-case is this codebase's correct, standard convention.
- **Restricting the `message` slot to `<li>` elements only** — rejected in favor of any element type; the `<ul>` wrapper was replaced with a plain `<div>` to match, which also fixed an actual accessibility violation (`<li>` outside a `<ul>`/`<ol>`).
- **Building Playwright/visual-regression tests as requested by the ticket** — deferred to a follow-up infrastructure ticket after discovering the repo has zero Playwright configuration or dependency.
- **"Fixing" a reported comment-node bug in `handleDefaultSlotChange` that doesn't actually exist.** A review tool claimed a framework's conditional-rendering placeholder could be misread as real default-slot content. A fix and a regression test were written, but the test passed identically whether the fix was present or not — the DOM spec defines a "slotable" as only an Element or a Text node, so `handleDefaultSlotChange` can never observe a comment node in the first place, confirmed empirically. The speculative fix and its non-discriminating test were both reverted; a clarifying comment was left in place of a code change.
- **A reported `<li>` bullet-marker bug in the `message` slot, investigated and found to have no real usage to fix.** A review pass observed `<li>` elements slotted roughly 25 times throughout the test suite, with no `<ul>`/`<ol>` wrapper, and concluded consumers were likely doing the same — flagging a missing `list-style` reset as a real, user-facing defect. Checking every actual example and doc file showed none had ever used `<li>`; it was a leftover artifact from this project's original `<ul>`/`<li>`-only design (already reversed once, above) that never got cleaned out of the tests when that design changed. Rather than add a defensive CSS reset for a pattern nobody uses, the stale `<li>` fixtures in the test suite were replaced with `<span>`, matching every real example.
- **Two revisions of the rotating example messages before landing on order-agnostic wording.** The original messages ("Checking your bags…" → "Confirming your seat…" → "Almost there…") were first replaced with "Checking flight status…" → "Loading your boarding pass…" → "Fetching the latest offers…", which dropped the explicit "almost done" ending but still read as three sequential steps in an airport check-in flow — wrapping from the third phrase back to the first still looked like the process had gone backward. Replaced again with "Hang tight…" / "Thanks for your patience…" / "This may take a moment…", interchangeable reassurances with no implied order.
- **Extending the font-weight safety net to every new size class as the size-scaling feature was built, instead of questioning whether the safety net itself was sound.** The `--wcss-body-xs/sm/lg-weight` additions mechanically followed the pattern of the existing `--wcss-body-default-weight` fallback without re-examining whether an unconditional `:host`-scoped fallback was the right shape for that pattern to take. It wasn't — see Root Cause #13 — and the entire fallback was removed rather than kept in its extended form.
