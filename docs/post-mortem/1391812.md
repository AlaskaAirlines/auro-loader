# AB#1391812

## Executive Summary

Today, the `auro-loader` spinner is just an animation — it can't tell a guest what's happening or why a wait is taking a while. This work adds an **optional descriptive message** next to the loading animation, which can also **rotate through several messages** over time (for example, "Checking your bags…" → "Confirming your seat…" → "Almost there…"). Teams can also choose which side of the animation the message appears on (top, right, bottom, or left). Guests who have "Reduce Motion" turned on see the most relevant text available — their custom fallback text if they set one, otherwise the message content rather than a generic "Loading…" — and never see two competing pieces of text at once. Nothing about this changes how any existing loader already in use looks or behaves — the feature is entirely opt-in. Two rounds of independent code review, plus hands-on testing, caught and closed a series of real defects along the way, including two separate cases where a claim of "no visual change" turned out to be wrong until it was fixed and re-verified.

Ticket: [AB#1391812](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1391812)

## The Problem

Many of Alaska's loading states are open-ended — the app can't say how long a spinner will keep spinning. With no way to pair the spinner with reassuring text, a 15–25 second wait can feel like the app is stuck, which increases the chance a guest gives up and abandons what they were doing. The native app already solves this by pairing its loader with rotating reassurance text; this work brings the web experience to the same standard.

## The Fix

`src/auro-loader.js` gained a new named slot, `message`, that accepts one or more elements of any type:

```html
<auro-loader orbit message-position="top" message-interval="4000">
  <span slot="message">Checking your bags...</span>
  <span slot="message">Confirming your seat...</span>
  <span slot="message">Almost there...</span>
</auro-loader>
```

- **Slot tracking**: a `slotchange` handler reads `assignedElements()` from the `message` slot and toggles the native `hidden` attribute on each element to show exactly one at a time — no re-rendering or re-parenting of consumer-owned nodes. Any element type rotates, not just `<li>`; the internal wrapper is a plain `<div>` rather than a `<ul>` (a `<ul>` requiring `<li>` children was the original design, but restricting to `<li>` was reversed — see Iterations below).
- **Cycling**: a `messageInterval` property (`message-interval` attribute, default `5000`ms) drives a `setInterval` that only starts when more than one message is slotted and the type isn't `laser`. The timer is always cleared before a new one is set, cleared again on `disconnectedCallback`, restarted from index 0 whenever the slotted content changes mid-cycle, and restarted in `connectedCallback` too (covering a DOM move/reparent that fires disconnect→connect without a `slotchange`). `_advanceMessage` guards against an empty message list to avoid a `NaN` index.
- **Interval validation**: falls back to the 5000ms default whenever `messageInterval` isn't a finite positive number, closing a runaway near-0ms timer bug. `updated()` now also self-corrects the *property* back to `5000` (not just the effective timer delay), so an invalid `message-interval="abc"` doesn't linger in the DOM reflected as the literal, confusing attribute `message-interval="NaN"`.
- **Positioning**: a `messagePosition` property (`message-position` attribute: `top` | `right` | `bottom` | `left`, default `bottom`) controls `:host`'s flex-direction. An invalid value (e.g. a typo like `"buttom"`) self-corrects back to `bottom` the same way, rather than silently no-op'ing with no matching CSS rule and no warning.
- **Accessibility**: the message region carries `role="status"`, `aria-live="polite"`, `aria-atomic="false"`; `::slotted([hidden])` is hardened with `!important` so a consumer's own `display` rules on the slotted elements can't defeat the rotation. Under reduced motion, rotation stops entirely and **freezes on whichever message was active** when the preference took effect — it does not reset to the first message (documentation previously claimed otherwise; see Root Cause).
- **Reduced motion, fully content-aware**: two `slotchange`-driven host attributes — `has-message` and `has-default-content` — track which slots actually have real content (as opposed to the default slot's built-in `Loading...` fallback). Both the default slot's fallback text **and** the `message` region are gated on these attributes, so exactly one piece of text is ever shown: the default slot's real content if it has any, otherwise the message, otherwise the generic fallback.
- **`laser` type**: the `message` slot (and the pre-existing default/static-label slot) is never shown for `laser`, in any motion state, and no rotation timer runs for it — matching `laser`'s pre-existing, intentional lack of room for text.
- **Styling**: placeholder CSS custom properties (`--ds-auro-loader-message-color`, `--ds-auro-loader-message-spacing`), marked `TODO(design)`, plus a new `_message.scss` partial.
- **Layout restructuring**: the spinner's spans/svg were wrapped in a new `.loader-shape` container so `:host` could become a flex container laying out the animation and the message region together, while leaving `:host`'s rendered size identical when no message is present. `:host` also kept its `position: relative`, restored after review caught that the restructuring had silently dropped it.
- **Stylelint cleanup**: the touched SCSS files (`color.scss`, `style.scss`, and the `base`/`laser`/`orbit`/`pulse`/`ringworm`/`message` partials) were brought to zero stylelint errors — flat combinator selectors converted to proper SCSS nesting, property order and duplicate-selector issues fixed, and the handful of violations that are structurally unavoidable (the `.loader-shape` wrapper necessarily produces selectors one level deeper than `selector-max-combinators`/`selector-max-compound-selectors` allow) or intentional (this project's kebab-case class names vs. the shared config's default camelCase pattern) are suppressed with a `stylelint-disable` and an explanatory comment — not silently worked around. The near-identical explanatory comment was originally duplicated across all 6 files; it now lives once, canonically, in `_base.scss`, with the other 5 files linking back to it.
- **CEM/manifest accuracy**: `onDark`/`onLight` now carry an `@deprecated` JSDoc tag (previously only prose said "DEPRECATED", which generated JSX/Svelte types never picked up) and an explicit `attribute: "ondark"`/`"onlight"` mapping, so the generated manifest's attribute name matches what actually binds in HTML instead of the untransformed property name.
- **Dependency-driven CSS regression closed**: `tokens.scss` now defines `--wcss-body-default-weight: 450` on `:host` as a safety net, restoring the concrete `font-weight` this component's fallback/message text (`.body-default`) lost when `@aurodesignsystem/webcorestylesheets` moved that token's value into a separate global theme stylesheet this component doesn't import (see Root Cause).

## Root Cause

Five unrelated defects surfaced across three rounds of review, each worth recording on its own:

1. **Reduced-motion visibility gating was asymmetric.** `event.target.assignedNodes({ flatten: true })` on an *empty* default slot returns the slot's own fallback content (the `Loading...` text node), not nothing — an unguarded flatten call could see "content" a consumer never provided, latching `has-default-content` permanently true. Separately, the CSS gating which text shows under reduced motion was applied to only one side of the pair: `.message-region` was correctly gated, but `.no-animation` (the default-slot fallback) had no matching gate and was `display: block` unconditionally, so a `message`-slot-only consumer could see both texts at once. Both fixed by symmetric, content-aware gating on `has-message`/`has-default-content`.
2. **A mechanical stylelint re-nest silently dropped a property.** The pre-existing `pulse` loader relied on `:host([pulse]) > .loader-shape > span { position: relative; }` to override the base `.loader-shape > span { position: absolute; }`, so its three dots would lay out inline via `margin` instead of stacking at the same coordinates. When `_pulse.scss` was restructured into nested SCSS to fix unrelated stylelint errors, `position: relative` was preserved on `:host([pulse])` and on `.loader-shape`, but never re-added to the innermost `> span` block — a straightforward copy-and-restructure slip, not a logic change, but the resolved CSS was silently different afterward. This is a second, independent instance of the same category of defect as the original `.loader-shape` wrapper regression from the first round of work (see Iterations): touching shared/inherited CSS structure without diffing the *resolved* output before and after.
3. **A geometry-based regression test can be defeated by an unrelated animation.** The first attempt at a regression test for defect #2 asserted that the three pulse spans' `getBoundingClientRect().left` values were distinct. It passed even with the bug reintroduced, because `pulse`'s `@keyframes` animation combined with each span's staggered `animation-delay` puts every span at a slightly different point in its `transform: scale()` cycle at the instant the assertion runs — enough to produce slightly different bounding rects regardless of whether `position` was actually correct. The fix was to assert directly on `getComputedStyle(span).position === "relative"` instead of an indirect geometry side-effect, then prove it by reverting the CSS fix and confirming the test failed before restoring it.
4. **A shared library moved a design token without a compatible fallback.** `@aurodesignsystem/webcorestylesheets`'s `.body-default` class (used by this component's fallback and message text) reads `font-weight: var(--wcss-body-default-weight, )` — note the empty fallback. That token's concrete value (`450`) now lives only in the package's theme stylesheet, which `auro-loader` never imports. Consumers who separately load Auro's global theme never noticed; anyone who doesn't would silently get the browser's default font-weight. Two independent code-review tools (a two-model `xhigh` review and a separate, differently-scoped review skill) each found this independently by diffing the dependency's compiled CSS across versions, not by reading source. Fixed defensively — not by pinning the dependency back down, but by defining the same custom property, with the same value, directly in this component's own `tokens.scss`, so it no longer depends on an external stylesheet being present.
5. **A property self-correction ran in the wrong Lit lifecycle hook.** The `messageInterval`/`messagePosition` self-correction (defect resolutions above and in an earlier round) was originally written inside `updated()`. Mutating a reactive property from `updated()` — after the current render has already completed — is a documented Lit anti-pattern: it schedules a brand-new update cycle rather than folding into the one already in progress, which a review tool confirmed by actually running the test suite and observing Lit's own runtime warning ("scheduled an update ... after an update completed," see `https://lit.dev/msg/change-in-update`). The practical effect was an invalid value briefly reaching render/use before being corrected, plus a wasted extra render pass every time. Moved to `willUpdate()`, which runs *before* the render it's guarding and is exactly where Lit's own docs recommend this kind of pre-render property correction.

## Why This Works

The `message` slot is fully independent of the existing default (unnamed) slot — there's no shared markup or selector between the two, so populating one never interferes with the other's own rendering. Toggling `hidden` on the slotted elements (rather than re-rendering them) keeps consumer-attached state/listeners on those nodes intact and gives the accessibility tree a single, predictable mutation per cycle for the live region to announce. Gating the interval behind `_messages.length > 1` and `!this.laser` means a single message or a `laser`-type loader never spins up a needless timer, and clearing the timer unconditionally before setting a new one (on slot change, on interval-property change, on connect, and on disconnect) rules out leaked or duplicate timers regardless of how the element enters or leaves the DOM.

The reduced-motion behavior is symmetric by construction: both text sources are gated by the same pair of attributes, so there is no code path where both are visible at once, and no code path where neither is. The pulse-dots fix is narrow and mechanical by design — a single restored property, verified against the *compiled* CSS output (not just the SCSS source) to confirm the resolved selector once again matches what shipped before this branch. The improved regression test is more trustworthy specifically because it was validated adversarially: reverting the real fix and confirming the test fails is what separates a test that happens to pass from a test that actually constrains the behavior.

## Outcome

Loaders across the product can now carry a short, optionally rotating message — of any content type, not just plain list items — that tells guests what's happening during a wait, without any visual or behavioral change to loaders that don't use the new capability. Teams also get control over which side of the animation the message appears on. Guests with "Reduce Motion" enabled always see exactly one, correctly-chosen piece of guidance text, frozen on whichever message was showing rather than jumping back to the first one. A dependency bump riding along with this branch no longer silently changes the fallback/message text's font-weight for consumers who don't load Auro's global theme.

Four rounds of independent review (two `xhigh`-effort two-model code reviews plus two passes of a third, differently-scoped review skill) surfaced and closed a long list of real defects: a reconnect/cycling-stops bug, a `laser` incompatibility, a real `npm run lint` failure, a test-isolation leak, an interval-validation gap, an incomplete reduced-motion fix, a slot-fallback-detection bug, a documentation/behavior mismatch about which message freezes under reduced motion, a visual regression on the pre-existing, unrelated `pulse` loader type introduced by this branch's own stylelint cleanup, a dependency-driven font-weight regression, a missing validation guard on `messagePosition`, an invalid value leaking into the DOM as a literal `"NaN"` attribute, duplicated maintenance-cost boilerplate across 6 SCSS files, and — found only by a tool that actually ran the code and read the browser console — a Lit lifecycle anti-pattern in the property self-correction logic. 32 automated tests now cover the new slot, cycling, cleanup, accessibility attributes, positioning (including invalid-value fallback), the `laser` exclusion, the content-aware reduced-motion behavior, non-list-item content, and the `pulse` layout regression specifically.

## Learnings

- **Mechanical refactors of shared/inherited CSS need the resolved output diffed, not just the source.** Two separate incidents in this branch — the original `.loader-shape` wrapper hiding every animation type, and this round's stylelint re-nest dropping `position: relative` from `pulse` — were both "the source looks like a faithful restructuring" mistakes that only a compiled-CSS comparison (or, in the second case, an adversarial test) caught. A model reviewing the same diff can plausibly assert it's a faithful re-nesting and be wrong, as happened here.
- **A geometry assertion (`getBoundingClientRect`) is not a reliable proxy for a static CSS property when an animation is in play.** `transform: scale()` driven by a `@keyframes` animation with staggered `animation-delay` shifts bounding rects independent of `position`, producing a false negative (test passes when it shouldn't). Assert directly on `getComputedStyle(...).position` for this kind of check instead.
- **"No visual change" is a claim that needs to survive an adversarial check, not just a plausible read of the diff.** Both `.loader-shape` incidents shipped with that exact claim in a commit message or post-mortem before being disproven by review. Where feasible, verify by reverting the fix and re-running the relevant test/visual check, the same discipline already used for logic bugs.
- **A dependency version bump can change compiled CSS output even when nothing in the repo's own source changed.** Bumping `@aurodesignsystem/webcorestylesheets` changed a CSS custom property's fallback value because the shared library moved a token to a different stylesheet. "The tests still pass" doesn't catch this class of defect when nothing in the test suite pins the resolved value of a shared design token's fallback. When a defect can't be fixed by pinning back to the old dependency version (already needed for other reasons), define the same fallback locally instead of depending on an external stylesheet being present.
- **Independent review tools finding the same defect by different methods is a strong signal, not a coincidence to shrug off.** The `webcorestylesheets` font-weight regression was caught three separate times across this branch's history — by two different `xhigh` two-model reviews and by a third, differently-scoped review skill — each arriving at it by actually diffing compiled/dependency output rather than reading the diff statically. When multiple independently-run tools converge on the same non-obvious finding, that's a reason to prioritize fixing it, not a reason to suspect it's a false positive.
- **A validated property (`messageInterval`) can make an adjacent, unvalidated one (`messagePosition`) look more correct than it is.** Both were added in the same feature; only one got a validation guard. Reviewers correctly flagged the asymmetry — when one property in a small, related group gets defensive handling, check whether its siblings need the same treatment before calling the group done.
- **Self-correcting a reactive property belongs in `willUpdate()`, not `updated()`.** Mutating `this.someProp` inside `updated()` happens after the current render already completed, so Lit schedules an entirely new update cycle for it (and warns at runtime that this happened) instead of folding the correction into the render already in progress. `willUpdate()` runs before that render, which is exactly where Lit's own docs point for this pattern. Caught only by a review tool that actually ran the test suite and read the resulting browser console warning — a static read of the diff would not have surfaced this.
- Lit does not auto-hyphenate camelCase property names into kebab-case attributes — needs an explicit `attribute:` mapping or the HTML attribute is silently ignored (bit this project twice, and separately caused the `onDark`/`onLight` manifest-accuracy fix in this round).
- `assignedNodes().length > 0` is not a valid "has content" check — it counts whitespace-only text nodes between tags, which exist in virtually every real multi-line usage of a slotted component.
- CSS specificity, not source order, decides who wins inside a media query: an attribute selector on `:host` beats a bare `:host` even when the bare rule is the one wrapped in the more specific media query.
- `<auro-loader>` has no default animation — every animation is opt-in via a boolean type attribute (`orbit`, `pulse`, `ringworm`, `laser`). Documentation examples must always pair with one of these.
- Uncommitted work on a long-running branch is fragile: at multiple points across this feature's history, a previously-made change silently disappeared from the working tree between turns with no corresponding edit, most plausibly from git side effects of automated review tooling interacting with fully uncommitted state. Committing incrementally (as this branch now does) removes that risk going forward.
- This repo's generated `docs/api.md` (via the older `web-component-analyzer` CLI) is broken by an earlier, unrelated housekeeping commit that deleted `scripts/wca/auro-loader.js`; it's hand-maintained now and needs manual updates kept in sync with JSDoc, which is how the reduced-motion wording bug was able to drift into three separate hand-maintained locations in the first place.

## Iterations That Didn't Work

- **A stylelint-driven restructuring of `_pulse.scss` that silently dropped `position: relative`.** The re-nest into proper SCSS syntax (to fix unrelated combinator/compound-selector violations) preserved `position: relative` on the outer `:host([pulse])` and `.loader-shape` levels but not on the innermost `> span` block, causing the three pulse dots to stack instead of laying out inline. Caught by code review, not by the existing test suite (the existing "should have three elements" test only counted `<span>`s, so it passed regardless of layout). Fixed by restoring the property and adding a test that asserts the computed `position` value directly.
- **A `getBoundingClientRect()`-based regression test for the pulse fix.** The first version compared each span's `left` coordinate, expecting the bug to make them identical — but the `pulse` animation's `transform: scale()` with staggered delays perturbs bounding rects regardless of `position`, so the test passed even with the bug deliberately reintroduced. Replaced with a direct `getComputedStyle` assertion after verifying via revert-and-retest that the new version actually fails without the fix.
- **Hiding only the `message` region under reduced motion, leaving the default-slot fallback unconditional** (from an earlier round) — replaced with symmetric, content-aware gating on both sides.
- **Freezing the message on reduced motion instead of hiding it, then hiding it unconditionally** (from an earlier round) — both replaced by the current content-aware behavior, with the documentation now correctly describing the "freeze on last-active message" behavior that the code already had.
- **`.loader-shape` wrapper shipped without updating dependent selectors or preserving all of `:host`'s prior properties** (from an earlier round) — broke every loader type's visibility and separately dropped `position: relative` from `:host` itself; both caught by user report and code review respectively.
- **Renaming classes to camelCase to satisfy the shared stylelint config's `selector-class-pattern` rule.** Done broadly across all touched SCSS files before the person driving the work caught it: kebab-case is the correct, standard CSS convention for this codebase, and the rule itself was the mismatch. Reverted every rename and used a justified `stylelint-disable` instead, consistent with how the other structurally-unavoidable rule violations in this same cleanup were already being handled.
- **Restricting the `message` slot to `<li>` elements only** (from an earlier round) — rejected in favor of any element type; the `<ul>` wrapper was replaced with a plain `<div>` to match, which also fixed an actual accessibility violation (`<li>` outside a `<ul>`/`<ol>`).
- **Building Playwright/visual-regression tests as requested by the ticket** — deferred to a follow-up infrastructure ticket after discovering the repo has zero Playwright configuration or dependency; the second review round's own recommended follow-up work reached the same conclusion independently, citing the `pulse` regression as a concrete example of what that coverage would have caught.
