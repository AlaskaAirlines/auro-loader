# AB#1391812

## Executive Summary

Today, the `auro-loader` spinner is just an animation — it can't tell a guest what's happening or why a wait is taking a while. This work adds an **optional descriptive message** next to the loading animation, which can also **rotate through several messages** over time (for example, "Checking your bags…" → "Confirming your seat…" → "Almost there…"). Any kind of content can be slotted in — not just list items. Teams can also choose which side of the animation the message appears on (top, right, bottom, or left). Guests who have "Reduce Motion" turned on see the most relevant text available — their custom fallback text if they set one, otherwise the message content rather than a generic "Loading…" — and never see two competing pieces of text at once. Nothing about this changes how any existing loader already in use looks or behaves — the feature is entirely opt-in. Two rounds of independent code review, plus hands-on testing, caught and closed several real defects along the way, including one in an earlier fix that hadn't fully worked as claimed.

Ticket: [AB#1391812](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1391812)

## The Problem

Many of Alaska's loading states are open-ended — the app can't say how long a spinner will keep spinning. With no way to pair the spinner with reassuring text, a 15–25 second wait can feel like the app is stuck, which increases the chance a guest gives up and abandons what they were doing. The native app already solves this by pairing its loader with rotating reassurance text; this work brings the web experience to the same standard.

## The Fix

`src/auro-loader.js` gained a new named slot, `message`, that accepts one or more elements of any type:

```html
<auro-loader orbit message-position="top" message-interval="4000">
  <span slot="message">Checking your bags...</span>
  <span slot="message">Confirming your seat...</span>
  <span slot="message">Almost there...</span>
</auro-loader>
```

- **Slot tracking**: a `slotchange` handler reads `assignedElements()` from the `message` slot and toggles the native `hidden` attribute on each element to show exactly one at a time — no re-rendering or re-parenting of consumer-owned nodes. Any element type rotates, not just `<li>`; the internal wrapper is a plain `<div>` rather than a `<ul>` (a `<ul>` requiring `<li>` children was the original design, but restricting to `<li>` was reversed — see Iterations below).
- **Cycling**: a `messageInterval` property (`message-interval` attribute, default `5000`ms) drives a `setInterval` that only starts when more than one message is slotted and the type isn't `laser`. The timer is always cleared before a new one is set, cleared again on `disconnectedCallback`, restarted from index 0 whenever the slotted content changes mid-cycle, and restarted in `connectedCallback` too (covering a DOM move/reparent that fires disconnect→connect without a `slotchange`). `_advanceMessage` guards against an empty message list to avoid a `NaN` index.
- **Interval validation**: falls back to the 5000ms default whenever `messageInterval` isn't a finite positive number, closing a runaway near-0ms timer bug.
- **Positioning**: a `messagePosition` property (`message-position` attribute: `top` | `right` | `bottom` | `left`, default `bottom`) controls `:host`'s flex-direction.
- **Accessibility**: the message region carries `role="status"`, `aria-live="polite"`, `aria-atomic="false"`; `::slotted([hidden])` is hardened with `!important` so a consumer's own `display` rules on the slotted elements can't defeat the rotation.
- **Reduced motion, fully content-aware**: cycling stops entirely under `prefers-reduced-motion: reduce`. Two `slotchange`-driven host attributes — `has-message` and `has-default-content` — track which slots actually have real content (as opposed to the default slot's built-in `Loading...` fallback). Both the default slot's fallback text **and** the `message` region are now correctly gated on these attributes, so exactly one piece of text is ever shown: the default slot's real content if it has any, otherwise the message, otherwise the generic fallback. An earlier version of this rule only gated the `message` region, leaving the fallback text unconditional — a bug caught by code review and fixed in this same work (see Root Cause / Iterations).
- **`laser` type**: the `message` slot (and the pre-existing default/static-label slot) is never shown for `laser`, in any motion state, and no rotation timer runs for it — matching `laser`'s pre-existing, intentional lack of room for text.
- **Styling**: placeholder CSS custom properties (`--ds-auro-loader-message-color`, `--ds-auro-loader-message-spacing`), marked `TODO(design)`, plus a new `_message.scss` partial.
- **Layout restructuring**: the spinner's spans/svg were wrapped in a new `.loader-shape` container so `:host` could become a flex container laying out the animation and the message region together, while leaving `:host`'s rendered size identical when no message is present. `:host` also kept its `position: relative`, restored after review caught that the restructuring had silently dropped it — consumers positioning something over the loader depend on that.

## Root Cause

Two related but distinct defects sit behind the "reduced motion" behavior, both traced to the same underlying fact: **a slot's fallback content and a slot's assigned content are not the same thing, and telling them apart correctly is easy to get wrong.**

1. `event.target.assignedNodes({ flatten: true })` on an *empty* default slot returns the slot's own fallback content (the `Loading...` text node) — not nothing. An unguarded flatten call could therefore see "content" that was never provided by a consumer, latching the `has-default-content` attribute permanently `true` after a framework (React, Vue) rendered then removed real default-slot content. Fixed by only flattening when `assignedNodes()` (unflattened) already found something.
2. The CSS gating "which text shows under reduced motion" was applied to only one side of the pair: `.message-region` was correctly gated on `has-default-content`, but `.no-animation` (the default-slot fallback) had no matching gate — it was `display: block` unconditionally whenever reduced motion was active. The result: a consumer using only the `message` slot would see **both** the generic fallback and their real message at once under reduced motion, the exact "two competing pieces of text" scenario the feature was supposed to prevent. Fixed by adding the mirror-image rule, `:host([has-message]:not([has-default-content])) > .no-animation { display: none; }`.

## Why This Works

The `message` slot is fully independent of the existing default (unnamed) slot — there's no shared markup or selector between the two, so populating one never interferes with the other's own rendering. Toggling `hidden` on the slotted elements (rather than re-rendering them) keeps consumer-attached state/listeners on those nodes intact and gives the accessibility tree a single, predictable mutation per cycle for the live region to announce. Gating the interval behind `_messages.length > 1` and `!this.laser` means a single message or a `laser`-type loader never spins up a needless timer, and clearing the timer unconditionally before setting a new one (on slot change, on interval-property change, on connect, and on disconnect) rules out leaked or duplicate timers regardless of how the element enters or leaves the DOM.

The reduced-motion behavior is now symmetric by construction: both text sources are gated by the same pair of attributes, so there is no code path where both can be visible at once, and no code path where neither is (the generic fallback is the ultimate default when neither slot has real content). This is a stronger guarantee than the earlier "hide the message region unconditionally" rule, which relied on `.message-region` alone doing the right thing regardless of what `.no-animation` was doing.

Removing the `<li>`-only filter and switching the wrapper from `<ul>` to `<div>` isn't just a preference — keeping `<li>` semantics while allowing arbitrary elements produced actually-invalid HTML (a `<span>` as a list item's sibling inside a `<ul>`), and the accessibility test caught the inverse case immediately: axe flags `<li>` elements that aren't inside a `<ul>`/`<ol>` as a serious violation. A generic `<div>` wrapper has no such content-model constraint, so any element type is now both functionally and semantically correct.

The `laser` exclusion is grounded in an actual CSS-specificity finding: `:host([laser]) { display: block; height: 0; overflow: hidden; }` is unconditional and has higher specificity than the bare `:host { display: flex; }` inside the reduced-motion media query, so it wins regardless of motion state — meaning `laser`'s fallback text was already invisible in every motion state before this change (confirmed by compiling the SCSS). That's an intentional design constraint for `laser`, not a bug, so the `message` slot (and its timer) follow the same rule rather than becoming the one exception.

## Outcome

Loaders across the product can now carry a short, optionally rotating message — of any content type, not just plain list items — that tells guests what's happening during a wait, without any visual or behavioral change to loaders that don't use the new capability. Teams also get control over which side of the animation the message appears on. Guests with "Reduce Motion" enabled always see exactly one, correctly-chosen piece of guidance text — never two competing pieces, never the wrong one. Two independent multi-model code reviews (run at the highest review effort level) were performed against this change; together they surfaced and closed: a reconnect/cycling-stops bug, a `laser` incompatibility, a real `npm run lint` failure, a test-isolation leak, an interval-validation gap, an incomplete reduced-motion fix that still showed two texts at once in one specific scenario, and a slot-fallback-detection bug reachable by dynamic frameworks. A further defect (the `<li>` content-model violation) was caught by the project's own accessibility test the moment the `<li>`-only restriction was lifted. 30 automated tests now cover the new slot, cycling, cleanup, accessibility attributes, positioning, the `laser` exclusion, the content-aware reduced-motion behavior (including toggling the preference mid-cycle), and rotation of non-list-item content.

## Learnings

- **A slot's fallback content and its assigned content are easy to conflate.** `assignedNodes({ flatten: true })` on an empty slot returns the fallback content itself, not an empty list — any "does this slot have real content" check must special-case this (e.g., check unflattened `assignedNodes()` first).
- **A reduced-motion / content-visibility rule needs to be checked from both sides.** Gating only one of two mutually-exclusive things (the message region) and leaving the other (the fallback text) unconditional recreated the exact "two texts at once" bug the rule was written to prevent — just for the opposite case. When two states are meant to be mutually exclusive, verify both directions independently.
- **A passing test can still be a bad test, twice over in this feature.** Once, a test's single-line fixture markup happened to avoid the exact whitespace-text-node condition being tested. Later, lifting the `<li>`-only restriction was validated immediately by an *existing* accessibility test catching a real, independent violation (`<li>` outside `<ul>`/`<ol>`) — a reminder that broad, real assertions (like a full `to.be.accessible()` check) catch classes of regression that narrow, purpose-built tests don't.
- **Two agents editing the same uncommitted working tree concurrently is a real, encountered risk, not a hypothetical one.** In this session, a background code-review agent was — separately from the main assistant — given direct authorization to apply its own findings, while another review agent was mid-flight analyzing the same diff and the main assistant was independently discussing the same fixes with the user. All work landed correctly this time (independently verified: tests passing, diffs matching the report), but the coordination was accidental, not designed, and depended on the second agent proactively sending a heads-up. Nothing was committed at any point during this multi-agent activity, which is the condition that makes silent clobbering possible.
- **An unexplained dependency bump surfaced with no clear owner.** `package.json`/`package-lock.json` picked up updated `@aurodesignsystem` package versions (including a major version bump on `webcorestylesheets`, `^10.1.4` → `^12.0.1`) that neither the user, the main assistant, nor the agent that reviewed the diff caused knowingly. Left unresolved as of this post-mortem — worth tracing before merge, since a major-version bump to a stylesheet dependency can carry breaking changes unrelated to this ticket.
- CSS specificity, not source order, decides who wins inside a media query: `:host([laser])` (an attribute selector) beats a bare `:host` even when the bare rule is the one wrapped in `@media (prefers-reduced-motion: reduce)`.
- `<auro-loader>` has no default animation — every animation is opt-in via a boolean type attribute (`orbit`, `pulse`, `ringworm`, `laser`).
- `prefers-reduced-motion` can't be forced in headless WTR/Chrome by matching the real media query — but a test-only `matchMedia` override that can dynamically fire `change` events (rather than a static one-shot mock) makes the *component's* media-query-listener logic fully testable even though the CSS's own visual effect still can't be triggered this way.
- Wrapping existing shared DOM (spinner spans/svg) in a new container breaks every CSS selector elsewhere in the codebase written with a direct-child combinator assuming the old structure, and can silently drop unrelated properties (`position: relative`) that existing consumers may depend on — a full-repo audit of both selectors and properties is needed, not just a check of the touched file.
- Repo-wide `lint:fix` reformats far more files than the ones intentionally changed; scoping `biome check --write` to just the touched files avoids that blast radius.
- Uncommitted work on a long-running branch is fragile — at multiple points in this session, previously-made changes silently disappeared from the working tree between turns with no corresponding edit, most plausibly from git side effects of automated review tooling (`git add -N`/`git add`) interacting with fully uncommitted state. Committing incrementally would remove this risk going forward.
- This repo's generated `docs/api.md` (via the older `web-component-analyzer` CLI) is currently broken by an earlier, unrelated housekeeping commit that deleted `scripts/wca/auro-loader.js`; it's now hand-maintained and will keep drifting from JSDoc.
- Explicit user decision: proceed with clearly-marked placeholder design tokens rather than blocking implementation on a missing Figma/Design sign-off.

## Iterations That Didn't Work

- **Restricting the `message` slot to `<li>` elements only.** The initial design rendered the slot inside a `<ul>` and filtered assigned content to `tagName === "LI"`, treating the feature as a list of messages. The person driving the work rejected this — any element type should be able to rotate. Removing the filter meant the `<ul>` wrapper no longer made sense (and became actively wrong once non-`<li>` content was allowed), so it was replaced with a plain `<div>`; all example markup and one test fixture were moved from `<li>` to `<span>` to match.
- **Hiding only the `message` region under reduced motion, leaving the default-slot fallback unconditional.** This was believed fixed and documented as such after the previous round of work, but code review (independently, by two models) found that a consumer using only the `message` slot would see both the fallback and the message simultaneously — the fallback side of the rule had never been added. Fixed by adding the missing, symmetric CSS rule.
- **Using `assignedNodes({ flatten: true })` unconditionally to detect default-slot content.** Passed every test written against it, including the one specifically added to catch the whitespace-text-node version of this bug — but a reviewer found a dynamic-framework case (content rendered, then removed) where the flattened fallback text itself satisfies the "has content" check, latching the state permanently wrong. Fixed by checking unflattened `assignedNodes()` first.
- **Freezing the message on reduced motion instead of hiding it** (from the previous round) — stopped the cycling timer but left the last-shown message visible, which could render simultaneously with the default slot's fallback text. Replaced with a hide-based, later fully symmetric, rule.
- **`.loader-shape` wrapper shipped without updating dependent selectors or preserving all of `:host`'s prior properties** — broke every loader type's visibility (caught via user report) and separately dropped `position: relative` (caught by code review), both from the same underlying cause: restructuring shared DOM without auditing every consumer of the old structure.
- **Building Playwright/visual-regression tests as requested by the ticket** — deferred to a follow-up infrastructure ticket after discovering the repo has zero Playwright configuration or dependency.
- **Assuming the `laser` + reduced-motion text gap was a bug** — corrected by the person driving the work: it's intentional, pre-existing spec, which reframed the fix from "restore visibility" to "make the new `message` slot consistent with that existing spec."
